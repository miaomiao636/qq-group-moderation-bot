# AI辅助审核、动态规则与人工反馈学习设计

> **2026-09-07适用性说明**：本文档的AI、动态规则、反馈真值、候选规则和人工发布设计仍有效；其“QQ官方机器人影子链路”与 `OFFICIAL` 作为生产前提的假设已被决策D-019替代。目标大群将通过T-305/T-306的传输中立契约和NapCat/OneBot Adapter进入同一审核核心；本文档不能单独作为NapCat真实动作的开发或上线依据。

## 1. 目标与实施边界

本设计在现有 QQ 官方机器人影子审核链路上完成四项工作：

1. 修复已复现的并发去重、失败重试、媒体配额/文件名和规则误伤问题。
2. 将硬编码规则迁移为可在管理后台编辑、测试、发布、回滚并持久化的版本化规则。
3. 接入供应商可替换的远程文本/视觉 AI 审核能力，首选兼容 OpenAI API 的小米 MiMo，但不在领域代码中绑定供应商。
4. 将管理员人工判断沉淀为反馈样本，由系统生成候选规则，经回放评估和人工批准后发布。

本设计不启用 NapCat 自动踢人，不绕过 QQ 风控，不把模型输出直接转换为处罚，不把“未撤回”自动视为正常样本，也不进行无人监督在线训练。

## 2. 已验证的现状与问题

截至提交 `ce2f2f7`：

- 现有 160 项测试、mypy、ruff 均通过，但测试没有覆盖若干真实故障。
- 两个数据库会话可以同时领取同一条 `PROCESSING` 消息，存在重复处理和重复处罚风险。
- 永久解析失败先插入唯一 `shadow_decisions.message_id`，再次重试会触发唯一键冲突。
- 媒体目录只在下载前检查配额，下载完成后可超过上限；文件名只保留消息 ID 最后 24 个字符，存在碰撞；读取魔数时实际先把整个文件读入内存。
- `兼职`、`刷单` 等单词被视为直接处罚的硬证据，反诈讨论、否定句和询问句也会被判为高置信违规。
- 所有分享卡片都被 R006 直接判高置信违规，与允许“万能校园墙”来源的群规冲突。
- 规则仍是 Python 常量，`/admin/rules` 只读且缺少一致的登录保护，后台 POST 操作缺少 CSRF 保护。
- 运行器仍是影子模式，只监听 `GROUP_MESSAGE_CREATE`；尚无远程 AI 适配器、动态规则版本或管理员反馈学习链路。
- 项目记忆文档存在“尚未编写业务代码”等过期描述，与实际代码不一致。

## 3. 方案选择

### 方案 A：所有内容交给一个多模态模型

优点是接入快、组件少。缺点是每条消息都有远程成本，行为、二维码、重复内容和确定性群规难以稳定解释；音视频仍需抽帧和转写；模型故障会影响全部审核。

### 方案 B：文字模型与视觉模型完全独立

优点是可以分别优化精度、延迟和成本。缺点是首版要维护多个供应商契约、预算和故障模式，集成成本较高。

### 方案 C：分层级联审核（采用）

先执行本地确定性规则、行为检测、OCR、二维码、感知哈希和官方语音转写；只有无法确定的内容才进入文本或视觉 AI。文本与视觉使用独立任务接口，但可以由同一个 MiMo 供应商提供。最终由确定性策略引擎合并证据。

该方案兼顾成本、可解释性、隐私和可替换性，也是现有架构改动最小的方案。

## 4. 总体架构

```text
QQ GROUP_MESSAGE_CREATE
        |
        v
消息标准化 + 媒体安全下载
        |
        +--> 确定性层：动态规则 / 行为 / OCR / QR / 哈希 / ASR
        |
        +--> AI文本任务：原文、OCR、ASR、卡片、文件文本
        |
        +--> AI视觉任务：图片、GIF代表帧、视频代表帧
        |
        v
确定性策略合并器
        |
        +--> allow / record_only / violation_high
        |
        +--> 影子记录 / 官方撤回禁言编排（默认关闭）
        |
        v
人工反馈 --> 候选规则 --> 历史回放 --> 人工发布 --> 热更新
```

所有外部输入均视为不可信数据。群消息、附件文字和模型响应不能成为系统指令、工具参数或自由执行代码。

## 5. 第一阶段：核心正确性整改（R-103）

### 5.1 带租约的原子事件领取

`processed_events` 增加领取令牌、租约到期时间、尝试次数、下次重试时间和最终错误分类。

- 首次事件使用原子插入领取。
- `PROCESSING` 且租约未过期时，其他处理器必须返回“已在处理”。
- 只有租约过期才能重新领取，并生成新的领取令牌。
- 完成、失败或续租必须携带当前领取令牌，旧处理器不能覆盖新处理器状态。
- 永久契约错误进入 `DEAD` 并生成一次人工复核记录；网络或临时依赖错误进入 `RETRYABLE`，使用有限退避。

### 5.2 判定记录幂等

每个消息 ID 最多有一条当前判定记录。重复写入采用显式更新/幂等 upsert，不依赖捕获唯一键异常。永久解析错误成功保存后不再次重试；管理员仍能在后台查看错误原因和原始事件摘要。

### 5.3 媒体安全

- 文件名改用完整消息 ID 的 SHA-256 摘要加附件序号，不再截取尾部。
- 媒体下载由单一受控入口管理，下载前参考 `Content-Length`，流式过程中同时执行单文件上限和目录剩余配额检查。
- `.part` 临时文件计入配额；超限立即删除，最终重命名前再次核对。
- 只读取前 16 字节嗅探格式，不把整个媒体读入内存。
- 下载器并发通过进程内锁/单消费者约束串行更新配额；部署仍保持一个媒体工作器。未来多进程部署前必须升级为数据库或文件锁配额租约。

### 5.4 规则误伤修复

- `兼职`、`刷单`、`一单` 等单独出现只作为弱语义信号，不能直接触发处罚。
- 高置信广告需要“招募/收益/任务”等意图与联系方式、恶意域名、确认二维码、确认广告图或重复行为等独立证据组合。
- 否定、咨询、反诈教育、引用讨论进入 `allow` 或 `record_only`，不得自动处罚。
- 分享卡片先识别来源白名单和风险内容；允许来源直接放行，未知来源只记录，有明确引流证据才升级。
- 允许规则与禁止规则冲突时默认 `record_only` 并告警，不自动处罚。

### 5.5 后台基础安全

所有 `/admin/*` 页面统一要求登录。所有修改状态的表单使用 CSRF 令牌，登录会话采用安全 Cookie 属性和有限有效期。规则发布、回滚、反馈标注和动作模式切换都写入审计日志。

## 6. 第二阶段：动态规则系统（T-105）

### 6.1 数据模型

数据库保存：

- `rule_sets`：全局或指定群的规则集合。
- `rule_versions`：不可变版本，状态为 `DRAFT`、`ACTIVE`、`ARCHIVED`。
- `rule_items`：规则条目、类别、权重、作用域、启用状态和说明。
- `rule_audits`：创建、修改、测试、发布和回滚记录。

首版只允许安全的结构化规则类型：关键词、短语组合、允许/禁止域名、二维码载荷、分享来源、媒体哈希、联系方式组合和行为阈值。不允许管理员输入任意 Python、SQL、模板或不受限正则表达式。

### 6.2 规则优先级

1. 系统安全约束：保护角色、禁止自动踢人、媒体失败不处罚。
2. 明确且已确认的允许来源/白名单。
3. 已确认恶意域名、二维码、媒体哈希和行为规则。
4. 文字和 AI 软证据。

允许与禁止证据冲突时不自动处罚，进入人工复核。群级规则可以覆盖全局业务规则，但不能关闭系统安全约束。

### 6.3 后台流程

管理员可以创建草稿、编辑、停用、复制、模拟测试、发布和回滚。发布前必须显示：

- 规则差异。
- 对最近保留期内历史消息的回放影响。
- 新增高风险命中、可能误伤和冲突样本。
- 版本号和确认按钮。

发布后数据库 `ACTIVE` 版本成为权威。运行器按版本号缓存规则，最长 5 秒发现新版本并原子替换内存快照，无需重启。每条判定保存规则版本 ID。

## 7. 第三阶段：远程 AI 辅助审核（T-204）

### 7.1 供应商适配

定义与供应商无关的 `TextModerator` 和 `VisionModerator` 接口。首个适配器使用 OpenAI-compatible HTTP 协议，可配置 MiMo：

- `AI_ENABLED`：默认关闭。
- `AI_BASE_URL`：远程接口地址。
- `AI_TEXT_MODEL`：文本模型，例如 `mimo-v2.5-pro`。
- `AI_VISION_MODEL`：视觉模型，例如 `mimo-v2.5`。
- `AI_API_KEY`：仅从环境变量或系统凭据读取。
- 超时、最大并发、每分钟调用数、每日预算和熔断阈值。

真实 API Key 不写入代码、文档、测试、日志或 Git 历史。

### 7.2 分流

- 文本任务：原消息、卡片字段、OCR、官方 ASR、文件提取文本。
- 视觉任务：图片、最多 8 个 GIF 代表帧、最多 16 个视频代表帧。
- 行为任务：继续由确定性代码完成，不发给模型。
- 首版不把完整视频、完整文档或无关上下文上传云端。

### 7.3 固定输出契约

模型只能返回经严格校验的 JSON：类别、置信度、证据摘要、是否需要人工、模型 ID、提示词版本和响应耗时。缺字段、类型错误、超时、拒绝、限流或非 JSON 响应统一降级为 `record_only`。

模型不能返回或触发 `kick`、HTTP 调用、数据库语句、脚本或系统指令。模型建议必须经过策略合并器。

### 7.4 自动处罚边界

- 单个 AI 模型无论置信度多高，首版都只能提供软证据。
- 只有确定性硬证据，或“主模型不低于 0.90 + 配置为独立的复核模型确认”才能形成 `violation_high`。
- 同一供应商的两个提示词不默认视为独立模型。
- AI 未完成离线评测和至少 24 小时影子观察前，不参与自动处罚。

### 7.5 缓存、成本和隐私

缓存键包含脱敏内容摘要、媒体摘要、模型 ID、提示词版本和规则版本。按群配置是否允许云端 AI；发送前去除无关身份字段并遮蔽可遮蔽的联系方式。费用、延迟、命中率、失败率和熔断状态进入报告。

## 8. 第四阶段：管理员反馈与候选规则学习（T-205）

### 8.1 反馈来源

首版权威入口是管理后台：管理员在已记录消息或案件上标记“确认违规”“确认正常”“误撤”“其他原因撤回”，违规反馈必须选择类别并可补充简短原因。

QQ 官方机器人能否收到普通群管理员手工撤回事件尚未验证，因此不能作为首版前置条件。预留 `RecallFeedbackSource` 接口；NapCat/Milky 被动撤回事件只作为未来可选输入，必须在 T-303 获得单独批准后接入，离线时回退人工标注。

### 8.2 标签语义

- 管理员确认违规：正例。
- 管理员确认正常或标记误判：负例。
- 已撤回但原因未知：待标注，不作为训练真值。
- 未撤回消息：未标注，不自动视为正常。
- AI 或现有规则自己的结论不能反过来充当人工真值。

### 8.3 候选规则生成

定时任务从已确认反馈中提取重复短语、域名、联系方式组合、二维码载荷、分享来源、媒体哈希和行为模式。达到最低支持度后，AI可以总结并生成结构化候选规则；首版默认至少 3 条独立消息且来自至少 2 个成员才提出候选，阈值可配置。

候选规则只能使用动态规则系统允许的类型，不能生成任意正则、代码或处罚动作。每个候选记录来源样本、支持数、反例冲突、建议作用域和生成模型版本。

### 8.4 回放与发布

候选规则必须对保留期内消息回放，展示：

- 会新增命中的消息数。
- 已确认正例覆盖数。
- 已确认负例误伤数。
- 未标注样本预览。
- 与现有规则和群级白名单的冲突。

只有管理员登录、查看预览并确认后，候选规则才能复制为规则草稿；仍需经过动态规则的发布确认。系统不得自动发布或自动提高处罚等级。

## 9. 官方动作运行编排（T-106）

当前影子运行器保留。新增动作模式：

- `SHADOW`：默认，只记录建议。
- `OFFICIAL`：只允许官方撤回、禁言和首次警告；不包含踢人。

进入 `OFFICIAL` 必须同时满足：生产配置明确开启、数据库迁移为最新、管理员密码有效、QQ 凭据存在、紧急停止开关可用、W1/W2 对应测试通过。每个动作先写持久化意图和幂等键，再调用外部接口，再记录结果；结果未知时进入人工复核，不能盲目重放。

本设计只实现可测试的编排能力，默认配置仍为 `SHADOW`，不会在开发机或同步代码后自动处罚真实群。

## 10. 错误处理与降级

- 规则快照损坏：继续使用最后一个有效版本并告警；没有有效版本时只记录。
- AI 超时、限流、预算耗尽或熔断：只记录，不阻塞确定性硬规则；报告显示降级原因。
- 媒体失败：只记录并转人工，不能作为违规证据。
- 数据库写入失败：不执行外部动作。
- 外部动作结果未知：持久化为 `UNKNOWN`，等待查询或人工处理。
- NapCat 不可用：不影响官方审核和人工后台反馈。

## 11. 测试与验收

### 11.1 R-103

- 两个独立数据库会话并发领取同一事件，成功领取数必须为 1。
- 租约未过期不可重领，过期后可安全接管，旧令牌不能完成新任务。
- 永久解析失败重复投递不产生唯一键错误或多条判定。
- 配额在并发和流式下载中不能超过上限；文件名碰撞测试通过；大文件嗅探不全量读入。
- 反诈、否定、咨询、招聘白名单、允许卡片来源均不得自动处罚。
- 所有管理页鉴权和 POST CSRF 测试通过。

### 11.2 动态规则

- Alembic 升级、降级和旧常量初始化迁移可重复执行。
- 草稿不会影响运行；发布后 5 秒内热更新；回滚恢复旧版本。
- 冲突、越权、重复发布和并发发布被安全处理。
- 每条判定可追溯到规则版本。

### 11.3 AI

- 使用固定假响应测试文本、图片、超时、限流、非法 JSON、提示词注入和熔断。
- 未配置 Key、预算耗尽或 AI 关闭时应用仍可运行并安全降级。
- 日志和数据库不保存 API Key；上传负载不含不必要身份字段。
- 真实 MiMo 只在负责人本地配置 Key 后，用脱敏样本执行独立验证。

### 11.4 反馈学习

- 未撤回消息不被写为负例。
- 未知原因撤回不直接生成真值。
- 候选规则不能自动发布、不能包含不支持的规则类型或动作。
- 回放能识别确认负例误伤；发布和回滚完整审计。

### 11.5 全量门禁

每阶段必须通过 pytest、mypy、ruff check、ruff format、Alembic 升降级、构建和 Git 修改范围检查。远程 Linux/Windows CI 必须真实通过；涉及真实 QQ 和 MiMo 的结果必须单独注明是否已实测。

## 12. 实施顺序和发布策略

1. `R-103`：先关闭当前正确性和后台安全缺陷。
2. `T-105`：动态规则、版本、后台编辑、热更新和回滚。
3. `T-204`：远程 AI 适配器与影子评测。
4. `T-205`：人工反馈、候选规则、回放和人工发布。
5. `T-106`：官方动作编排，但保持默认 `SHADOW`。
6. Windows W1/W2 和至少 24 小时影子观察通过后，才由负责人决定是否启用 `OFFICIAL`。
7. NapCat 被动撤回输入和踢人仍属于后续、单独批准的 T-303/T-304 范围。

各阶段独立迁移、测试和提交，不能把全部改动压成一个不可审查的大提交。
