## 交付的实际范围

首版保持一台 Windows、一套 QQ/NapCat、一个应用实例（禁止多 uvicorn worker）、SQLite WAL、服务端后台。按测试证据逐种声明支持的消息类型：接收到“语音/文件/转发”不代表成功理解内容。未安装的 OCR/ASR、无法展开的转发、下载或分析失败必须转人工，不能写成已覆盖的自动审核能力。

自动动作仅撤回、首违禁言 3,600 秒并警告一次、同群同人 30 天内第二次禁言 86,400 秒且不再警告、生成待审案件。踢人由人工 QQ 客户端执行；T-304 自动代执行不是本轮交付前置。

`ONEBOT_ACTION_STAGE=recall_only`默认只执行撤回；负责人明确批准在本机改为full并重启，才执行完整阶梯。它是全局阶段，配合逐群action_enabled控制试点，不是每群不同阶段配置。仅撤回期间仍累计有效违规，切full不清零历史。可用新的同意受测成员验证首违，禁止清库或删真实处罚记录。

## 人工接管：目前最重要的交付缺口

D-015 现有通知渠道是**管理后台页面**，不是短信、邮件或即时消息推送。若承诺无人值守，必须先由客户选择并授权一个能够主动到达值班人的渠道，最好独立于被监控的 QQ 账号和本机进程；未接通、未实测送达/确认/升级处理前，不得宣称“异常会自动通知到人”。本轮不擅自创建账号、发送外部消息或接入收费服务。

## 独立样本与可重复报告

- 人工标签只表示该条样本，不表示所有含同一短语的消息都违规。未知撤回与未被撤回均不是正常真值。
- 每个交付类别至少准备 20 个独立正例、30 个正常/难负例作为最低覆盖起点；这是覆盖下限，不是证明 99% 长期精确率的充分样本量。按相似广告模板分组分割，开发/候选挖掘集与留出集不得混用。纳入真实群正常内容比例的额外抽样，避免只测“明显广告”。
- 每轮冻结代码、模型 ID/供应商版本、提示词与规则版本、阈值；改过任何一项重新评测，不把不同版本结果混在一起。
- 人工复核命中不算“自动处罚召回”；报告另外给出发现召回、待审比例、实际响应时间与人工工作量。过量 record_only 不是安全成功，而是可能压垮管理员的容量风险。

本机 JSONL 每行仅允许以下元数据；示例是虚构的格式示范，**不可计入验收**：

```json
{"sample_id":"synthetic-example","label":"confirmed_normal","verdict":"allow","category":"ad","kind":"image","latency_ms":1200,"model_revision":"frozen-model-id","rule_revision":"frozen-rule-id"}
```

`label` 允许 confirmed_violation/confirmed_normal/false_positive；`verdict` 允许 allow/record_only/violation_high；类别允许 ad/fraud/porn/violence/flood/other；类型允许 text/image/gif/video/audio/file/share_card/mixed/unknown。类别表示人工设定的评测类别，不能只用模型预测类别给漏报分类。latency_ms 从事件进入系统到最终判定，包含排队、下载与条件复核；动作延迟另表测量。

```powershell
uv run python -m app.reports.evaluation --input <本机脱敏样本.jsonl> --output <新的报告.json>
```

工具不调用模型、不读生产 DB、不自动给出验收通过、不覆盖已有报告。无分母输出 null。原始群内容、群号/QQ号、签名媒体URL、密钥与私密证据不得提交 GitHub；只有已脱敏的聚合报告、版本和校验摘要可以提交。

## 更新、备份和回滚

1. 在原 Windows 环境查看实际服务名、运行目录、数据库绝对路径和是否有未提交修改；不要凭文档硬编码路径覆盖现有部署。
2. 激活数据库急停、关闭按群动作；停止本项目写数据库的所有进程，确认无活跃事务后备份数据库及必要证据。SQLite WAL 有活动连接时不能只复制主文件；可用SQLite在线备份接口，或全部写进程停止后备份完整数据库文件集合。备份在受控路径保留并验证可读。
3. 固定合并后的代码版本，安装锁定依赖，运行 `uv run alembic upgrade head`。R-105迁移保留旧表，新增provider设置/审批计划/inbox；历史动作位全部安全关闭。不要迁移后自动恢复处罚位。
4. 默认SHADOW重启**单个**Web/OneBot进程，官方通道运行器只有确有使用才启动。不要 `--reload` 或多worker；这不是横向扩容实现。独立进程的急停通过DB共享，但会话/连接/模型额度是单实例边界。
5. 恢复备份只在暂停服务且关闭动作时进行；恢复后的旧待处理/已执行记录可能与QQ真实状态不同，逐项人工核对，UNKNOWN不得直接重放。不要在生产直接 downgrade base 或删除DB。
6. Windows 10普通支持已于2025-10-14结束，核验这台机器有效的延长安全更新和补丁状态，或另行安排升级。支持依据：[Microsoft Windows release health](https://learn.microsoft.com/en-us/windows/release-health/release-information)。不因已有历史补丁号就断言当前受支持或未受支持。

后台“创建一致性数据库备份”已使用实际DATABASE_URL的SQLite在线备份接口并检查完整性，包含已提交WAL记录；目录是实际DB同级 `backups/`，不是固定工作目录。不包含媒体与凭据，也不是异机备份。原件和副本都含私密数据，限制NTFS访问，按明确保留策略清理，别随PR上传。实现依据：[Python sqlite3 Connection.backup](https://docs.python.org/3.12/library/sqlite3.html#sqlite3.Connection.backup)。

## 持续有效：比继续增加模型更重要的工作

工程风险判断：最应先防的是QQ/NapCat更新、登录验证、账号权限或Windows运行环境变化造成收不到消息/执行不了动作，而后台仍有人误以为在工作；其次是广告模板变化、允许推广例外变化与待审队列无人处理。双模型并不能解决断流或无人接管，也不天然独立：不同模型ID可能仍使用相似模型与数据，置信度0.90不是实测90%正确率。

- 先缩小可签收范围：首批优先文字和经实测的图片广告/诈骗，未验证类型只转人工；把客户允许的招聘、合作推广、来源、白名单和申诉规则写成可测试的正反例。
- 明确规则优先，疑难才调用第二模型；不能用两个模型同意覆盖明确允许规则或内容缺失。人工反馈是本条真值，经候选、回放、人工发布形成版本化规则，不是自动训练模型，也不保证样本外正确。
- 每天核对输入是否正常、积压、动作失败/UNKNOWN、待审未处理和真实AI调用；不要把缓存当外呼或把未核算费用显示为免费。结合供应商账单定预算，调用次数上限不能代替精确的金额硬限。
- 每周抽查允许消息以发现漏报，复核全部误伤/申诉与高风险动作；衡量“少暴露多少违规、误伤多少正常、管理员花多少时间”，而不只看模型命中率。
- 每次改群规、模型或QQ/NapCat版本，先用固定留出集和恢复演练回归，再小范围灰度；保留已验证版本和可实际执行的回退路径。定期做异机备份恢复，不用“有备份文件”代替“能恢复”。

客户签收应同时明确服务时间、人工接管人及替补、响应目标、支持群/类型/规模、账号中断风险、AI费用承担、隐私与保留策略、维护更新责任。缺少这些时，软件功能完成仍不等于可持续运营的服务。
