# 诊断：为什么"带小程序码的图片"会被撤回（负责人 2026-09-18 反馈）

日期：2026-09-18
触发：负责人反馈"有人发带小程序二维码的图片被撤回了，其他人也有这个情况"。
性质：**只读诊断**（生产库 + 媒体文件 + 代码），未做任何修改；未把图内文案写入仓库。

---

## 1. 结论速览

1. **本次具体案例（含负责人截图那条）符合现有口径，不是系统乱撤**——图内是兼职/账号类广告，
   视觉模型判 `ad`/`fraud` ≥0.90 → 按 D-022 自动撤回。其中"支付宝亲密号"那条属**严重类别**，
   按负责人 2026-09-15 的 **B-2 口径（严重类别不因校园墙外观豁免）本就应当撤回**。
2. **但项目确实有 5 个缺陷**，导致"本该放行的校园墙图"失去**全部本地保护**，判定完全依赖
   单个远程视觉模型——模型一旦漏判就会误撤，且没有任何本地兜底。
3. 逐张抽查 4 张被撤原图，**均为真广告**；未发现直接误撤实例。但
   `category=ad 且证据提到校园墙/小程序` 的记录共 **32 条**，**需人工复核**才能确认误撤率
   （本诊断不逐条判定，也不作为"误撤率"结论）。

## 2. 图片类判定的实际链路（今日实测）

今日（UTC 00:00 起）图片类高置信违规 **237 条**：

| 观察项 | 实测 |
| --- | --- |
| 规则命中 | 几乎全部**只有** `AI_VISION`（`rule_hits=[('AI_VISION', ..., 0.35)]`），**本地规则 0 命中** |
| 证据 | `ai_results = [('vision','primary','ad'/'fraud', 0.90–0.98, needs_review=False)]` |
| **无独立二审的比例** | **201 / 237 ≈ 85%**（仅单主模型） |
| 触发口径 | D-022：主模型 ≥0.90、无冲突、needs_review=false → 直接形成高置信建议 → 撤回+禁言+警告 |
| 本地图片引擎 | 输出 `record_only`（"证据不足转人工"），随后被 AI 结果覆盖 |

**含义**：图片类处罚在实践上由**单个远程视觉模型**决定。这与 `PROJECT_CONTEXT.md` 的原始原则
（"单个模型只提供软证据；未配置独立复核模型时，AI 结果不直接触发自动处罚"）不一致——
目前是由 D-022 覆盖，但该覆盖从未按"单模型风险"评估过。

## 3. 五个缺陷（按严重度）

### P0-1 本地图片黑/白名单**当前完全失效**

- `QQBotRuntime` 每次启动都打印：`[runner] WARN: sample manifest not found, image lists empty`。
- `data/t002_media/`（负责人 2026-09-05 逐张确认的 8 张样本 + `manifest.json`）**已不存在**；
  项目内其它位置也**没有可恢复副本**（已核查 `data/`、`purge_drill`、`docs/`、`D:\QQ`）。
- 影响：**"带校园墙码=允许"的哈希白名单**与**违规图哈希黑名单**双双为空
  → 本地豁免（放行）与本地拦截（违规）**同时失效**，只剩远程模型。
- 根因：白名单种子是**原始图片文件**，`runner._seed_image_engine()` 每次启动用 `dhash()` 重算；
  而 `data/t002_media` 在 `app/reports/cleanup.py` 的 `_MANAGED_COPIES` 中登记为
  **15 天保留的"T-002 时代归档"** → 原图被清理后**哈希没有持久化，白名单永久丢失**。

### P0-2 "校园墙文案"放行信号是**死代码**

- `app/moderation/image_engine.py` 的 `_CAMPUS_WALL_MARKERS = ("长按识别小程序码", "一起看吧")`
  —— 全仓库**只有定义、没有任何调用点**。
- 模块 docstring 声明的第 5 条规则（"存在'长按识别小程序码'等校园墙分享文案 → 来源放行信号"）
  **从未实现**。负责人截图里那句"长按识别小程序，一起看吧~"本该触发放行。
- ⚠️ 实现边界：该文案是**微信小程序卡片的通用页脚**，若单纯按文本豁免，会把竞品小程序的
  广告一并放行（"挂羊头卖狗肉"固有风险）。需与负责人确认后才可实施（建议：必须"视觉确认为
  校园墙码"才算来源，文案仅作辅助）。

### P0-3 小程序码**天然不可解码** → 二维码白名单机制对小程序码无效

- `imaging.decode_qr_codes()` 用 zxing 解码；微信小程序码是加密编码，**解不出来**
  （`imaging.py` 注释亦承认"属预期行为，不作为处罚依据"）。
- 于是"解码二维码 → 与白名单载荷比对"这条路**对小程序码从设计上就不成立**；而本应兜底的
  P0-2 又没实现 → 带小程序码的图片**没有任何本地豁免**。

### P1-4 校园墙白名单命中只到"转人工"，不是"放行"

- 实测两条被模型**正确识别**为 `校园墙白名单|文案:…` 的图片，最终 verdict 是
  **`record_only`（转人工）**，而非文档/提示词写的"放行"。
- 影响：不会被撤回（安全），但白名单内容持续堆积人工队列，与 `docs/group-rules.md` 语义不符。

### P1-5 图片处罚缺少本地/独立兜底

- 见 §2：85% 无二审。模型漏判校园墙特征或误判时**没有第二道闸门**；提示词里"校园墙特征 +
  非严重类别 → 不判 ad"的约定**只依赖模型自觉**。

## 5. 建议修复（按优先级）

1. **哈希持久化（P0-1）**：新增表保存"已确认违规 / 已确认允许"的图片哈希；
   `runner` 改为**从库加载**（原图只在首次登记时使用）。这样清理原图不再影响白名单。
   **需要负责人重新提供那 8 张样本**（原图已丢，无法自动恢复）。
2. **校园墙豁免重建（P0-2/P0-3）**：与负责人确认实现边界后落地——
   建议"仅当视觉结构化确认为校园墙码/海报时才放行，文案特征只作辅助"。
3. **语义对齐（P1-4）**：白名单命中改 `allow`，或把文档/提示词改为"转人工记录"。
4. **收紧自动处罚（P1-5）**：图片类要求"二审确认或本地证据支持"才自动处罚；若决定保留
   D-022 的单模型口径，应写进 `PROJECT_CONTEXT.md` 并明确承担该风险。
5. **抽样评估**：对今日 237 条图片处罚人工抽样（建议 ≥30 条）估算真实误撤率，
   作为是否立即收紧的决策依据。
