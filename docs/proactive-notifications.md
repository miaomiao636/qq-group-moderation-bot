# 主动通知与外部健康监测（R-106）

状态：代码已实现，所有通知默认关闭；实际本轮验证见 PROGRESS。未在 Windows 配置或发送真实通知，本文件不是实机送达证明。

## 范围与边界

- QQ 固定管理员群：新增待审案件、动作结果 UNKNOWN 及时提醒；普通 `record_only` 每 15 分钟汇总。首次启用只发一条存量待办摘要，不逐条补发历史记录。
- 独立邮件：持续故障及恢复；QQ 通道明确失败或结果未知时转邮件告知。紧急事项 15 分钟未确认，升级给配置的备份管理员邮箱一次。
- Windows 任务计划每分钟运行一次独立探针：带专用只读令牌访问本机 `/health/ready`，健康才向 Healthchecks 发成功信号；不健康发失败信号。整机停电/断网时，由机器外的监测服务发现信号缺失并通知负责人。
- 通知不是处罚。管理员“确认接手”不批准案件、不踢人、不改规则或真实动作开关。群消息和通用 Agent 不能指定通知收件人、URL 或邮件正文。
- 不注册外部账号、不打开通知开关、不发送真实通知、不部署 Windows；负责人在本机配置并授权实测。邮件被服务接受、QQ 返回成功都不等于管理员看见。

## 故障与接管问题

需要能回答：目前审核是否真的就绪？是否有未接手的高优先事项？提醒是否被通道接受、失败还是未知？故障恢复后是否避免继续升级？

| 级别 | 来源与阈值 | 处理 |
|---|---|---|
| page（需要及时接手） | 新待审案件、UNKNOWN 动作 | QQ 主提醒；查看后台并确认接手，不盲目重放动作 |
| page | QQ 非就绪、审核 worker 退出、积压最老任务超过 5 分钟；同模型/审核角色最近 5 分钟至少 3 条连续失败，或已知未接管的邮件最终失败/UNKNOWN；持续 90 秒 | 邮件；检查账号登录、输入/处理队列与供应商，必要时人工接管 |
| ticket（可批量处理） | 新 record_only | 15 分钟一条数量摘要，后台逐条复核 |
| recovery（恢复记录） | 观察到恢复且 60 秒内无新故障 | 邮件一次，关闭原故障的升级；恢复通知不自动恢复处罚 |

阈值是首版可验证的默认策略，不是已承诺的 SLA。没有新群消息、没有 AI 调用都不单独算故障。已发生的 AI 故障必须看到同模型/角色的新非缓存成功才开始恢复观察，静默/缓存/另一个模型不能报恢复；不额外调用模型做探针。采样每轮最多读取最近 5 分钟 1,000 条非缓存日志，通知不是每个供应商独立 SLA 监测。

数据库读写失败或应用退出交由外部健康探针发现，因为损坏的数据库不能可靠存自己的故障通知。健康探针检查 DB 实际写入、QQ 就绪、审核任务存活、待处理任务年龄、通知 worker 最近成功轮询，以及未接管的邮件最终失败/UNKNOWN和超过5分钟的待发积压。它不能证明每条消息都被上游推送，也不证明闲时 SMTP 持续可投递；只有真实发送/接收演练能证明到人。

## 持久化与投递安全

通知、各通道投递、人工确认与采集水位保存在新增独立表。事件键去重，先落库再外呼，领取与结果写回使用令牌防止并发覆盖。确定未发送可最多尝试三次（60/300秒退避）；发送结果未知、退出后遗留发送中记录在120秒租约到期后标为 UNKNOWN，不自动重放。外呼前终检人工确认/恢复状态，后排未发项停止；跨过实际发送边界的请求不能保证撤销，不能假装已经取消。

默认每30秒采集；每批最多领取4条，先给每个启用通道预留1个名额，剩余按先进先出补齐，各通道内串行、QQ与邮件并行。这样一方积压或等待发送不会饿死另一方，批次上限仍为4；不是端到端送达时限保证。未启用QQ但已启用邮件时业务提醒改走邮件；都未启用时仅保存后台事项。QQ失败/UNKNOWN转邮件摘要，不递归报警。首位接管人15分钟未确认且事项未恢复时，向备份邮箱升级一次（时间可配置）；未配置备份邮箱不会假装升级成功。短期摘要被通道接受后可结束提醒，这不表示待审消息已经复核完成。群内“成员违规警告”和这里的“管理员提醒”是两种独立功能。

通知正文仅包含系统产生的记录编号、数量与固定说明，不含群消息、QQ 号、图片、媒体地址、令牌或模型原始回答。SMTP 只允许校验证书的 TLS；外部心跳仅允许固定 Healthchecks HTTPS 地址、禁止重定向且不携带业务数据。健康端点使用独立令牌，不复用管理员或 Agent 写令牌。日志只记录固定事件码与内部通知编号。

迁移 `d3f5a7b9c111`（父版本 `c2e4f6a8b010`）只增加表；上线前备份。关闭总开关并重启可停止采集和外发，不必删除通知数据。通知元数据按现有判断保留期清理，未接手/未关闭的事项保留。UNKNOWN来源和QQ回退提醒另留仅内部记录号的去重标记，不能因清理旧通知而重复通知；标记随来源动作生命周期保留，目前来源动作不自动清除。生产环境不要直接降级删表，测试回退仅用临时数据库。

## Windows 配置与运行

先从 [R-106 PR #6](https://github.com/miaomiao636/qq-group-moderation-bot/pull/6) 核对最终三项检查、合并状态和精确SHA（不是只更新到PR #5），保护本机修改和凭据，按交付清单备份、锁定依赖并迁移。保持 `ACTION_MODE=SHADOW`、`ONEBOT_ACTIONS_ENABLED=false`，不要为了测通知开启处罚。所有通知参数见 `.env.example`；服务和任务使用受限 Windows 账户读取本机配置，不把口令放任务命令行、截图或PR。

1. 负责人指定仅含管理员的 QQ 群、首位与备份接管人、值班时段。确认机器上的 QQ 已加入该管理群，配置固定 `ONEBOT_SELF_ID`、入站令牌、`NOTIFICATION_QQ_GROUP_ID`。QQ提醒还要求 `ONEBOT_WS_ENABLED=true`、NapCat反向连接实际ready；同时保持 `ONEBOT_ACTIONS_ENABLED=false`、`ACTION_MODE=SHADOW`，不要误把接入开关当成处罚开关。通知不支持靠群名或自然语言猜群，不接收任意群成员在 QQ 中回复“确认”。
2. 邮件填 `SMTP_HOST/PORT/SECURITY/FROM/USERNAME/PASSWORD`，收件人填 `NOTIFICATION_EMAIL_TO`、`NOTIFICATION_EMAIL_BACKUP_TO`（逗号分隔裸邮箱地址）。STARTTLS一般587、隐式TLS一般465，实际以邮箱服务文档为准；不支持降级明文。使用专用邮箱授权凭据，不使用QQ登录密码。
3. 外部负责人建立 Healthchecks 检查，设置 Period=1分钟、Grace=2分钟，配置并验证独立收件人；从最后一个成功信号起约3分钟没有新信号时应报警，实际延迟以演练记录为准。`/fail`显式失败信号可能立即报警，3分钟不是它的等待时间。先暂停检查完成配置/维护，收到健康信号后再启用，防止部署过程误报。心跳URL只存在本机安全配置，当前仅支持官方 `hc-ping.com` UUID 地址，不是任意Webhook。
4. 配置至少32位随机、专用 `NOTIFICATION_HEARTBEAT_PROBE_TOKEN`，不复用任何管理或OneBot令牌；`NOTIFICATION_HEARTBEAT_LOCAL_PORT`必须与实际 `WEB_PORT`一致。探针只访问127.0.0.1，若Web不监听回环地址需先采用受支持的本机监听方案；不要把管理后台暴露公网来迁就探针。
5. 获准后逐个启用 `NOTIFICATIONS_ENABLED` 和所需QQ/EMAIL/HEARTBEAT子开关，再重启单个应用实例。仅修改 `.env` 不会自动改变正在运行的发送器。首次启用仅摘要旧待办，之后新案件与UNKNOWN转换独立去重；不要通过删除水位“重置”通知。
6. 在Windows任务计划配置每1分钟运行一次以下命令：

```powershell
uv run --no-sync python -m app.notifications.watchdog
```

任务需使用实际 `uv` 绝对路径，起始目录为实际项目根；无论用户是否登录均运行，机器启动后恢复，禁止重叠实例，单次限时45秒。也可用已安装环境的Python绝对路径执行同一模块，不能使用依赖开发终端的会话。不要在Codex里创建线程定时器代替客户机器的计划任务。本次只提供实现和步骤，未替客户注册任务。

退出0表示本次健康信号已被服务接受，或功能关闭且明确打印skipped；退出1表示不健康/未确认送达。不能只看退出0而忽略skipped。本机QQ已断开时即使探针收到503，也应完成失败信号发送；整机断网/关机则无法发送，由外部服务检测缺失。

Healthchecks通知与升级配置独立于本地数据库：整机停机时后台不可用，本项目不能再计时发15分钟升级。外部检查必须同时配置首位和备份收件人及负责人认可的提醒策略；不要把应用内15分钟升级当作停机后仍能保证的SLA。外部服务的收件人不是 `NOTIFICATION_EMAIL_TO` 自动同步的。

后台 `/admin/notifications` 仅真人登录，确认接手具有CSRF与审计保护。通知正文只给内部编号，管理页仍仅本机/可信内网；手机从外网无法访问本机地址时用既有受控远程接管方式，不新增公网暴露。案件决定、解除禁言、踢人仍走原审批/人工QQ流程。

## Windows 验收表（全部需要实际取证）

| 场景 | 必须观察的结果 |
|---|---|
| 默认全关 | 不访问QQ发送、SMTP、Healthchecks；原SHADOW处罚零调用 |
| 管理群提醒 | 合成新案件、UNKNOWN转换仅一条；无群内容/QQ号；后台编号能找到原记录 |
| 人工接手/超时升级 | 真人确认有审计且后续待发升级停止；未确认到阈值备份邮箱仅一次；不生成任何处罚 |
| 疑难摘要 | 多条record_only批量一条，接收后提醒结束不等于业务已复核 |
| 通道自身异常 | QQ断开邮件仍可到人；邮件拒收/UNKNOWN反映到外部健康；恢复/确认后状态可解释，不盲目重发 |
| 停机与恢复 | 应用退出、QQ退出、DB锁定/不可写、断网、整机关闭分别可被正确发现；外部通知实际送达首位/备份；恢复后不会重放旧未知通知/处罚 |
| 低流量/AI | 静默正常群不报输入断流；AI故障不由缓存/静默/另一模型成功虚假恢复 |
| 重启/保留期 | 重启保留接手/升级/去重状态；清理不重弹已经接手的UNKNOWN提醒；备份还原要核对库外已发结果 |
| 页面 | 真人登录/退出、按钮键盘操作、窄屏长标题、分页、已确认/恢复/发送未知状态清晰；本轮浏览器控制不可用，此项未实测 |

每项记录代码SHA、脱敏配置开关、触发时间、通道返回时间、管理员实际收到时间、接手/升级时间与结果；不提交真实收件人、群号、凭据、心跳URL或原始消息。故障注入只在隔离测试配置中做，磁盘满/权限演练不得破坏真实证据库。

回退：先暂停外部检查的维护告警，关闭总开关、停止探针计划并重启应用；旧发送中事项保留UNKNOWN待核验。不删除通知表/水位，不自动恢复处罚。升级迁移的downgrade会删通知数据，只有停服务并明确备份/确认丢弃这部分数据后才可执行，生产通常无需降级。

## 实现依据

- [Healthchecks 外部缺失信号监测](https://healthchecks.io/docs/monitoring_cron_jobs/)；[Pinging API](https://healthchecks.io/docs/http_api/)：HTTP 200不单独证明UUID有效，代码还校验固定响应体；不上传业务内容。
- [Python SMTP](https://docs.python.org/3.12/library/smtplib.html) 与 [异步任务取消/线程](https://docs.python.org/3.12/library/asyncio-task.html)：SMTP接受不等于人收到，部分接受/发送后中断为UNKNOWN；外层取消不能杀死已在工作的线程。
- [SQLAlchemy SQLite upsert](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#insert-on-conflict-upsert)：通知唯一键、状态领取与持久标记使用数据库原子边界。
